## Delivered

- Additive EF Core storage for site/room/entity configuration, five-minute telemetry, hourly aggregates, model versions, plans/steps, DHW cycles, control state, writer leases, command audit and fallback events.
- Account-owned Home Assistant connections with separate telemetry and control identities. REST/history/WebSocket telemetry maintains an account-scoped timestamped cache; the control client exposes only `number.set_value` for the account's exact `number.*` entity.
- HA URL, enablement, staleness limit, allowlisted entity and AES-256-GCM-encrypted tokens are stored per server-verified Daikin account. No global HA environment-variable or Docker-secret fallback remains, and token values, fragments and lengths are never returned or logged.
- Daikin writes resolve only the encrypted token belonging to the server-verified account and fail closed when it is missing. The global Daikin access-token setting remains isolated to accountless legacy/test compatibility and cannot be selected for an authenticated account.
- Five-minute HA history import/resampling that never overwrites live snapshots, plus WebSocket reconnection/backoff and a fresh REST snapshot after reconnect.
- Sensor unit normalization, bounds/rate/staleness checks, three-invalid exclusion, three-valid recovery, critical-room fallback and deduplicated room/hydraulic diagnostics.
- Forecast-aware 2R2C grey-box and COP training with held-out validation, heat-output/COP guards, nightly versioning, model-drift warnings, room-specific offset/inertia/disturbance profiles and 400-day raw retention. Synthetic critical-room fallback values protect control but are excluded from readiness and model training.
- Five-minute, duration-based DHW planner with ten-minute ONECTA starts, whole-cycle cost, empirical Eco/Comfort profiles, 90th-percentile reservation, 20-minute lock, lifecycle tracking, actual cost and two-sample 60 °C verification. Incomplete price coverage selects the earliest safe start with a conservative price instead of risking availability, and the cost includes the estimated space-heating comfort margin consumed by the cycle.
- EMHASS 15-minute/48-hour space-heating coordination with locked DHW capacity and a 45-second hard timeout. The official container's documented `opt_res_latest.csv` is shared read-only, freshness/columns/horizon are validated, and mutual-exclusion groups prevent simultaneous space heating and locked DHW use of compressor capacity. EMHASS receives runtime data only and cannot access HA.
- PI-based LWT deviation controller with anti-windup, rate/change limits, DHW/defrost freeze, latched write failures and audited fail-to-zero attempts. A P1P2 write is accepted only after a fresh matching Home Assistant state confirms the requested value.
- Sequential `Legacy` → `Shadow` → `LwtActive` → `FullActive` mode service, measured readiness gates, installation ownership, expiring database-backed DHW write exclusion, atomic writer handover and visible rollback.
- A signed, database-backed session reuses the server-verified Daikin identity for legacy and thermal functionality. All account APIs require that session, all authenticated mutations require antiforgery validation, and administrative operations still require the admin role.
- The login gate offers an accessible, read-only retry after a failed session check. It hides cached installation views while verification is failing and never renders raw proxy/identity-provider error responses. This follow-up is locally verified, not yet deployed.
- Shared production/test HTTP registrations verify signed sessions, revocation, account/API isolation, CSRF and admin authorization without starting control workers. Account APIs return explicit 401/403 instead of cookie-login redirects; admin discovery includes credentialless existing records without modifying them. These fixes are locally verified, not yet deployed.
- Failed logout is clearly reported without revealing raw server errors or falsely claiming success. Responsive navigation has valid list markup, distinct landmark names and non-overlapping mobile links; logout/retry and keyboard navigation are covered locally, not yet deployed.
- Room cards use actual sensor quality/exclusion metadata and distinguish current measurements, stored fallback values, stale/imported data and fetch failures. Only current valid readings get a comfort margin; valid cold rooms retain their warning. Dated event history preserves Information/Warning/ActionRequired without presenting old events as active alerts. These UI changes are locally verified, not deployed.
- Overall status now assesses the signed-in account's enabled sources, exclusion/recovery, numeric/boolean values, quality metadata, source, snapshot age and configuration freshness. It returns an additive explanation and cannot infer Valid from a critical-room fallback. The UI explains status, hides cached claims on fetch errors and ages green badges independently of polling. Actual numeric API enums are translated in the browser; mode requests retain the existing numeric JSON contract and all activation gates. These fixes are locally verified, not deployed, and do not modify any controller.
- Admin account deletion now fails closed with an explicit HTTP 409 before any token/role removal. The old handler falsely reported complete deletion while leaving authenticated sessions, HA access, auto-apply and thermal writers intact. The admin UI explains the block, never issues deletion requests, hides cached account data on failed permission/list checks and provides accessible read-only recovery. This source-only safety guard is not a complete deletion lifecycle and is not deployed; active-writer coordination and audit-retention policy must be defined before deletion can safely return.
- The account-scoped HA catalog now distinguishes unavailable/invalid/stale values, disconnected or superseded snapshots, and preliminary role/unit compatibility without touching sensor-health counters. Shared room/entity pickers preserve saved IDs through missing entities and fetch failures, explain compatibility and both timestamps, and expire old local approvals. HTTP, numeric-contract, keyboard, accessibility and 320-pixel flows are locally verified, not deployed. This is not collector-health or readiness approval; collector edge-case tests remain open.
- Account configuration revisions now invalidate old cache leases and wake a per-account reconnect manager. Subscription acknowledgement precedes a revision-bound REST snapshot; intervening events and removals merge atomically. Old callbacks, concurrent settings saves and commit/invalidation races are tested. UI distinguishes saved settings, connection, snapshot, retry and verified live status, rejects stale revisions and supports read-only recovery. These changes are locally verified, not deployed; write serialization is process-local for the existing single app instance.
- Non-finite values, conversion overflow, malformed attributes and missing/contradictory/unzoned raw timestamps are rejected through normalization, collection and history. Health counters use measurement time, distinct recovery readings and configuration revisions; disconnected cache and critical fallback cannot certify live telemetry. COP requires an explicitly inactive backup heater. HA history now requests full records, preserves unit updates and validates gaps/rates without touching existing live rows. Readiness checks required live quality and excludes imports from 21-day telemetry coverage. The mode wizard revokes stale/error approvals, keeps guarded Legacy rollback and has a corrected 320-pixel layout. This source-only delivery is not a complete audit of model/heating-day acceptance.
- Model training, readiness and the account-scoped model API now share fail-closed validation of saved metrics, timestamps, physical parameters and full held-out two-hour/day windows. Weather selection and room fitting do not use final validation data; invalid saved samples and unknown compressor/backup-heater phases cannot certify a new COP model. Completed local heating days require near-complete live evidence, actual space heating and, for curve tests, measured zero deviation plus critical comfort. Imports, gaps, duplicate plans and old Shadow periods cannot inflate these gates. The model UI explains missing/old evidence, distinguishes validation from activation, expires stale approvals and offers read-only error recovery. Local HTTP, synthetic training, DST, UI/accessibility and 320-pixel browser tests pass. Revision provenance and complete plan/control acceptance remain open. No deployment, controller change or active-mode approval is included.
- The coordinator and queued EMHASS worker require the account's validated 2R2C/COP models, verified power sign and a current planning-evidence snapshot before and after asynchronous optimization. CamelCase model parameters are read correctly; guessed model/COP replacements cannot become a new valid plan. Full solverhorizon, ordered steps, zoned 15-minute timeline, finite effect/temperature/cost, comfort, locked DHW capacity and recomputed objective are now checked before persistence. Active LWT consumes only a non-Shadow `Valid` plan with complete steps and current model/config fingerprint; it rechecks the exact plan and current step before a write. Live flow, DHW/defrost status and quality-marked room readings are separate active readiness/control gates. Invalid or revoked evidence returns safely to zero, and simulated comfort breaches remain visible blockers. Queue callers cannot receive a coalesced replacement's result, JSON comparison tolerates jsonb formatting, and expired attempts cannot complete or fail a renewed claim. Local evidence metadata is never sent to EMHASS. These changes are local only; PostgreSQL/external-call atomicity and full real planning-input acceptance remain open.
- Every new solver request and persisted plan is now bound to the account's exact quality-valid five-minute telemetry sample and latest price snapshot for its configured zone. Required sensor roles, representative live room temperature, hydronic consistency, phase state, forecast continuity and zoned quarter prices fail closed; asynchronous solve and plan consumption recheck the same content fingerprints. Missing forecast/price tails are explicit estimates with stored coverage and a derived plan-confidence value shown in Swedish UI. A tracked running DHW cycle remains reserved while space-heating COP uses weather-curve/envelope inputs instead of DHW conditions. Local input evidence is never sent to EMHASS. This is locally verified and not deployed; PostgreSQL concurrency and real Shadow acceptance remain open.
- Exact account-owned open DHW state is now part of solver and plan evidence: the reserved row ID, open-row count and a content fingerprint covering every mutable lifecycle field. Empty state is fingerprinted, so a cycle created during solve revokes the result; existing cycles are rechecked in the persistent worker, active-plan reader and final write boundary. After a valid solve the reservation and plan are persisted under a short serializable relational transaction and the final plan receives the database-assigned cycle ID. Foreign-account cycles are ignored and evidence never leaves the orchestrator. This is locally verified and not deployed; real PostgreSQL conflict behavior remains open.
- Estimated DHW duration, power phases and COP are now bound to an exact account-owned source fingerprint covering only validated completed cycles and continuity-checked five-minute samples. Explicit fallback profiles are fingerprinted too. A source change revokes queued results, stored plans and final write-boundary validation; stored profiles for an existing cycle remain tied to that cycle's exact ID. Foreign history is ignored and provenance stays inside the orchestrator. This is locally verified and not deployed; PostgreSQL concurrency and real Shadow acceptance remain open.
- New 2R2C/COP versions now store a SHA-256 commitment to their exact validated historical selection, account-owned enabled configuration, selection rule and logical algorithm version. Missing, malformed, cross-account or count-inconsistent evidence fails the shared model assessment closed; the additive `jsonb` migration leaves old versions explicitly unproven until retraining. The account API omits raw fingerprints, while the Swedish UI shows traceability and counts and independently rejects stale/contradictory contracts. This is locally verified and not deployed; build-digest binding, PostgreSQL concurrency and real Shadow acceptance remain open.
- Active model reads now automatically reselect and rehash the stored account-owned 2R2C/COP source with the same training rules. Historical edits, deletion, qualifying backfill, enabled configuration changes and COP power-sign changes revoke planning, readiness and UI approval; foreign-account rows remain isolated. The API exposes only safe source-validation metadata, and the Swedish UI distinguishes changed history from missing evidence. This is locally verified and not deployed; published-image verification, PostgreSQL performance/concurrency and real Shadow acceptance remain open.
- Model source evidence now also requires the binary's immutable source revision. Schema-1, missing, malformed or different-build evidence fails closed in training, readiness, API, solver and active-plan consumers. PR/container builds stamp the checked-out `github.sha`; Docker rejects missing, mutable-tag and zero revisions. The Swedish model view treats `BuildChanged` as a separate retraining reason, hides revoked metrics and shows a short revision only in advanced details. The workflow is prepared for signed container build attestation, but source stamping does not verify a signature; exact published digest, trusted workflow and reviewed commit still require release acceptance. Every different commit conservatively requires model retraining, not an automatic active-mode change.
- An explicit PostgreSQL 17 acceptance harness is designed to create a disposable loopback-only database, apply real migrations and verify the telemetry time-range index, 400-day/two-account source-revalidation latency, committed historical changes and serializable open-DHW write-skew. It always compiles but reports a clear skip unless the isolated harness supplies its guarded connection string. Harness discovery, Release compilation and PowerShell syntax are locally verified; the database-backed run remains open.
